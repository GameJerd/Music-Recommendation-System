# PRD: Hybrid Music Recommendation System

Oct 21, 2026

> **Scope change, Oct 22, 2026: the system is now content-based only.** No real listening data exists for this catalog, so collaborative filtering, the synthetic user generator, the hybrid blend (including the 70/30 anchor) and Gates 2–3 were removed. The hybrid version is kept at git tag `hybrid-v1`. Evaluation uses list-quality proxies with no user data, and `/recommend/user` builds a content profile from the user's logged events or picked seeds. Reasons and results are in `docs/decisions.md` ("Scope change"). The rest of this document is the original spec, kept unedited for reference.

## Overview and goals

We are building a hybrid music recommender, content-based plus collaborative filtering, served by a FastAPI backend, as a course submission. Given a seed track or a user, it returns a ranked list of songs plus a breakdown of how much each engine contributed.

The starting point is the [GeeksforGeeks music recommender](https://www.geeksforgeeks.org/machine-learning/music-recommendation-system-using-machine-learning/): TF-IDF on genre, artist and track name, then cosine similarity. That is 100% content-based, has no user model, ignores the dataset's audio columns and has no evaluation. We keep it as our baseline and build on it.

The data is the Kaggle Spotify 1921–2020 tracks dataset (about 170,000 tracks with audio features), plus a synthetic user dataset that we generate ourselves, because no real listening data is available.

**Goals**

- Recommend similar songs from a seed track (content) and personalised songs for a user (hybrid).
- Real collaborative filtering, trained on a synthetic user dataset we generate ourselves (see Data strategy).
- Honest offline evaluation against baselines, with every result tagged by the data it came from.
- A clean Python backend: scripts, tests and config files, no notebooks.

**Success criteria**

- Hybrid scores higher than popularity, content-only and CF-only on NDCG@10 on the held-out split, or we report plainly where it does not.
- `/recommend` answers in under 200 ms on the default scale tier (proposed target, to confirm).
- Anyone can reproduce every reported number with one documented command.

**Blend requirement.** A user with a few plays (5) gets about 70% content-based and 30% collaborative weight.

## Scope and non-goals

Version 1 covers the data-to-API pipeline and the evaluation, and nothing that needs real users at scale.

**In scope**

- Catalog ingestion and a feature pipeline built from the music dataset.
- Content engine, collaborative engine, hybrid blender, popularity baseline.
- REST API with interactive docs (FastAPI's `/docs` page doubles as the demo UI).
- A synthetic user-data generator, interaction logging and a retrain script.
- Offline evaluation (a script, not a written report) and a decision log.

**Non-goals**

- Audio streaming or playback.
- Login, accounts or auth: users are plain `user_id` strings.
- Deep-learning recommenders (two-tower, sequence models); at most a stretch item.
- Online or real-time retraining; retraining is a manual script.
- Production deployment at large scale (see Scale as a variable).

## Key decisions

Nine decisions shape everything else; each has its reason written down so later contributors know why.

| # | Decision | Why | Rejected alternative |
| --- | --- | --- | --- |
| 1 | Hybrid by weighted score fusion, with the weight depending on how much history a user has | Simple, explainable, tunable, and easy to ablate | Feature-level hybrid or one big neural model: harder to explain and test |
| 2 | Collaborative engine is ALS matrix factorization on implicit feedback, with item-item KNN as a baseline | Plays and likes are implicit signals; ALS is the standard fit and trains fast on sparse data | Explicit star-rating models: we will not have ratings |
| 3 | Content features are scaled audio features plus artist genre tags and release decade | The Spotify dataset has audio features per track but no lyrics and no track-level genre | Text only: nothing to match on without lyrics |
| 4 | Nearest-neighbour index, not a full song × song matrix | A dense float32 matrix for about 170,000 tracks is roughly 115 GB | The article's `cosine_similarity(X, X)` |
| 5 | Interaction data is synthetic, generated by us; live events are an optional second layer | No real listening data is available; the generator gives CF signal the content model cannot see | A public dataset we cannot join to this catalog |
| 6 | FastAPI + Pydantic, SQLite first, Postgres at larger tiers | Matches the brief; SQLite needs no setup | Flask or Django: no typed contracts |
| 7 | No notebooks: scripts, a package, tests, YAML config | Reproducible, reviewable, importable by the API | Notebooks for pipeline steps |
| 8 | Everything keyed by `track_id`, with a search endpoint for titles | Titles repeat; the article's title lookup breaks on duplicates | Lookup by track name |
| 9 | Blend anchored at 70% content and 30% collaborative for a user with 5 plays | A product requirement; the weight formula is derived to hit it | Freely tuned weights: no guaranteed behaviour for early users |

## Data strategy

Content features come from the Spotify 1921–2020 tracks dataset on Kaggle, and collaborative filtering trains on a user dataset we generate ourselves, because no real listening data is available.

**Content data.** The notebook's dataset appears to be the Kaggle Spotify dataset (`vatsalmavani/spotify-dataset`): roughly 170,000 tracks from 1921 to 2020 with Spotify audio features such as danceability, energy, valence, acousticness, loudness and tempo, plus year, popularity, explicit flag and artists. Companion files group the same data by artist, genre and year. Genres exist per artist, not per track, and there are no lyrics. The Kaggle page needs a login and the notebook would not load for me, so Phase 0 confirms the file list, columns, licence and a stable `track_id` (the Spotify `id`) with `scripts/audit_dataset.py`.

**Synthetic user dataset: how we generate it**

`scripts/simulate_users.py` builds users and their plays from the track catalog and writes `data/synthetic/interactions.parquet` and `users.csv`. It is seeded and config-driven, so one seed always gives the same dataset.

1. **Personas.** About a dozen taste personas, each a region of audio space (for example high-energy and danceable, or quiet and acoustic), a set of preferred decades and a few favourite artists. Each user mixes one or two personas and adds personal noise. Persona labels are saved for checks only and never used as model input.
2. **Visible and hidden taste.** A user's affinity for a track is `visible_share` × a match on audio features and era, plus (1 − `visible_share`) × a match on hidden per-track and per-artist factors that no content feature shows. The content model can only see the first part; collaborative filtering can learn the second from co-plays. Default `visible_share` is 0.5.
3. **Popularity bias.** Plays are sampled in proportion to affinity times a popularity prior taken from the dataset's popularity column.
4. **Activity levels.** Plays per user are heavy-tailed, with target shares so every evaluation bucket is full: 20% of users with 1–4 plays, 30% with 5–19, 35% with 20–99 and 15% with 100 or more. Default is 10,000 users and about half a million interaction rows.
5. **Events and time.** Plays carry timestamps inside listening sessions over a 90-day window. Likes become more likely as affinity rises, skips as it falls.
6. **Self-checks.** After generating, the script compares the per-user count histogram with the targets, checks the long tail of track popularity and the matrix density, and tests that users of the same persona co-play more than chance. Results go to `manifest.json` beside the data, with the seed and parameters.

**Honest limit.** We wrote the generator, so results show whether the pipeline recovers what we built in, not how it would do on real listeners. The README says so, and the evaluation script shows results at `visible_share` 0.2, 0.5 and 0.8, so readers can see how much the hybrid's advantage depends on our assumption.

**Other interaction sources.** The API still logs live play, like and skip events (`source=live`) so the retrain loop can be shown with real clicks. They are tagged and kept out of reported numbers unless stated. A public listening dataset is no longer planned, since none is guaranteed to overlap with this catalog.

**Interaction record**

```csv
user_id,track_id,event_type,weight,ts,source
u_00042,7lCrsNdipwOICCRHFNtOoy,play,3,2026-11-02T18:04:00Z,simulated
u_00042,3yyR7MXpeELxM4OvQhqfDX,like,1,2026-11-02T18:09:00Z,simulated
```

`source` is `simulated` or `live`, so either layer can be included or excluded in training and evaluation. Plays and likes become implicit confidence values for ALS using the standard confidence-weighting formula:

```latex
c_{ui} = 1 + \alpha \, r_{ui}
```

Here r is the weighted play and like count for user u and track i, and α is a tunable constant. Skips are logged but not used in version 1.

## Recommendation engine

The engine blends a content model and a collaborative model, and leans on content for new users and on collaborative filtering as a user's history grows.

**Models used**

| Component | Model or algorithm | Library | Trained? |
| --- | --- | --- | --- |
| Audio features | Standard scaling of the audio columns (danceability, energy, valence, acousticness, instrumentalness, liveness, speechiness, loudness, tempo), weighted | scikit-learn | Fit once |
| Artist and genre tags | Multi-hot or TF-IDF of the artist's genres, joined from the artist and genre files, plus release decade | scikit-learn | Fit once |
| Content neighbours | Cosine nearest neighbours over the combined vector | scikit-learn `NearestNeighbors`; FAISS at larger tiers | Index build |
| Collaborative (main) | ALS matrix factorization on implicit feedback | `implicit` | Yes |
| Collaborative (baseline) | Item-item cosine KNN on the interaction matrix | `implicit` or SciPy | Index build |
| Popularity baseline | Rank by play count | pandas | No |
| Hybrid | Weighted score fusion, per-user weight anchored at 30% collaborative for 5 plays | NumPy | Weights tuned on validation |
| Stretch | K-Means clusters over audio space for candidate filtering and diversity reports | scikit-learn | Fit once |

**Content engine.** Each track becomes one vector: scaled audio features, plus its artist's genre tags and release decade, each block weighted. With no lyrics, audio is the main signal, and the text matching from the GeeksforGeeks article survives only in the genre-tag block. Block weights are tuned on validation data. It serves two requests: tracks similar to a seed track, and tracks for a user, using the average vector of the user's liked and played tracks as a profile.

**Collaborative engine.** A sparse user × track matrix feeds ALS, which learns a vector per user and per track; a user's score for a track is their dot product. Defaults to tune: 64 factors, regularisation, iterations. New events for an existing user are folded in without a full retrain; a full retrain is a script.

**Hybrid blend**

1. Take the top candidates from each engine (200 each, configurable).
2. Normalise each engine's scores to 0–1 within the request.
3. Score each candidate with the user's weights, then return the top K with the breakdown.

```latex
s(u,i) = (1 - w_{cf}(u)) \cdot s_{content}(u,i) + w_{cf}(u) \cdot s_{cf}(u,i), \qquad w_{cf}(u) = w_{max} \cdot \frac{n_u}{n_u + k}
```

n is the user's interaction count. The weight is anchored on a requirement: at 5 plays (a few plays) a user gets 70% content and 30% collaborative, which fixes the starting values at w_max = 0.75 and k = 7.5. If tuning changes w_max, k moves with it to keep that anchor: k = 5 × (w_max / 0.3 − 1).

- **New user (n = 0):** content only, seeded by tracks or genres they pick, falling back to popularity.
- **New track (no CF vector):** content score only; its weight moves to the content side.
- **Heavy user:** the CF weight approaches w_max and never reaches 1, so content always keeps a share.

**How much of each, at the starting values**

| User plays (n) | Content-based | Collaborative |
| --- | --- | --- |
| 0 | 100% | 0% |
| 1 | 91% | 9% |
| 3 | 79% | 21% |
| 5 (a few plays, the anchor) | 70% | 30% |
| 9 | 59% | 41% |
| 30 | 40% | 60% |
| 100 | 30% | 70% |

The overall split we report is the average CF weight across evaluation users, since it depends on how much history they have.

## API

Seven endpoints cover search, recommendations and event logging; all inputs and outputs are typed Pydantic models, so `/docs` is the live contract.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/health` | Liveness, plus the loaded model version and scale tier |
| GET | `/tracks/search?q=&limit=` | Find a `track_id` from a title or artist |
| GET | `/tracks/{track_id}` | Track metadata |
| GET | `/recommend/similar/{track_id}?k=10` | Songs similar to a seed track (content; item-item CF blended in when data exists) |
| GET | `/recommend/user/{user_id}?k=10&mode=hybrid` | Personalised list; `mode` is `hybrid`, `content`, `cf` or `popular` |
| POST | `/events` | Log a play, like or skip for a user |
| POST | `/admin/reload` | Load the latest trained artifacts without restarting |

**Recommendation response**

```json
{
  "user_id": "u_0042",
  "mode": "hybrid",
  "cold_start": false,
  "weights": {"content": 0.65, "cf": 0.35},
  "items": [
    {"track_id": "t_10231", "track_name": "...", "artist_name": "...", "genre": "...",
     "score": 0.81, "content_score": 0.77, "cf_score": 0.88}
  ]
}
```

**Behaviour rules**

- Unknown `track_id` returns 404; bad parameters return 422.
- An unknown or empty-history user returns 200 with `cold_start: true` and the content-only path.
- Already-played tracks are excluded from a user's list by default.
- Training never runs inside the API; retraining is a script, then `/admin/reload`.

## Architecture

Two offline chains build a content index and a CF model, and the FastAPI service only loads them, so serving never trains. The code is a Python package plus scripts, with no notebooks.

```text
OFFLINE: scripts you run by hand
  Music dataset (Spotify tracks, audio features)
      -> Build features (scaled audio + artist genres)
      -> [Content index]            (nearest-neighbour index)

  Synthetic users (generated by us)
      -> Train CF (ALS on implicit feedback)
      -> [CF model]                 (user and track factors)

ONLINE: FastAPI service
  [Content index] --loaded at startup--> Content engine (seed track or user profile)
  [CF model]      --loaded at startup--> CF engine (ALS scores, new-user fold-in)

  FastAPI routes (/recommend, /search, /events)
      -> Hybrid blender (per-user weights)
      -> calls Content engine and CF engine
  FastAPI routes <-> SQLite (tracks and events)
```

Routes call the blender, the blender calls the two engines, and routes read and write tracks and events in SQLite. Events logged there feed the interaction table the next time you retrain.

**Project layout**

```text
music-recsys/

  src/recsys/

```

## Scale as a variable

Scale is one config value, `scale.tier`, that picks the index, storage and training settings; we default to tier S and keep the seams for the rest. The thresholds below are proposed, not measured.

| | Tier S (default, course demo) | Tier M | Tier L |
| --- | --- | --- | --- |
| Tracks | up to 250,000 (this dataset: about 170,000) | up to 1 million | beyond 1 million |
| Users | up to 10,000 | up to 1 million | beyond 1 million |
| Interactions | up to 1 million | up to 100 million | beyond 100 million |
| Content index | Exact cosine nearest neighbours in memory | FAISS approximate index | Vector database |
| CF training | ALS on one machine | ALS on one machine, larger batches | Distributed ALS (Spark) |
| Storage | SQLite + joblib artifacts | Postgres + artifact store | Postgres + feature store |
| Serving | Compute per request | Cache top-K per active user | Precomputed candidates + cache |
| Status | Built | Interface ready, not built | Out of scope |

Two rules keep this honest:

- Engines talk to a `NeighborIndex` interface (`BruteForceIndex` now, `FaissIndex` later), so moving tier changes config and one class, not the engines.
- Evaluation reports always print the tier, catalog size and interaction count they ran on.

## Evaluation

We judge the hybrid by ranking metrics on held-out interactions, against three baselines, with results broken out by how much history each user has.

**Split.** Per user, ordered by timestamp: the last 10% of interactions are test, the 10% before are validation, the rest train. Weights such as w_max and k are tuned on validation only. Tracks with no interactions in train form the cold-item test set.

**Models compared**

- Popularity (floor).
- Content only (the article's method, extended with audio features).
- CF only (ALS, plus item-item KNN).
- Hybrid.

**Metrics**

| Metric | What it tells us |
| --- | --- |
| Recall@10 and Hit rate@10 | Did the held-out tracks show up in the top 10 |
| NDCG@10 | Whether they showed up near the top |
| Catalog coverage | How much of the catalog the system ever recommends |
| Intra-list diversity | How different the 10 recommendations are from each other (1 minus mean pairwise cosine on content vectors) |
| Genre match@10 | Proxy for the content engine on seed-track queries; it is not accuracy |

**Experiments**

1. Results by user bucket: 1–4, 5–19 and 20+ plays, plus probe users with 0 plays created at evaluation time. This is where the hybrid should win and where the 70/30 anchor applies.
2. Cold-item test: hold out all of some tracks' interactions and check the hybrid still recommends them.
3. Ablations: audio only vs audio + genre tags; sweeps of w_max (with k kept on the anchor) and ALS factors.
4. Sensitivity to the generator: repeat the main comparison at `visible_share` 0.2, 0.5 and 0.8, and report all three.

Every results table is generated by `scripts/evaluate.py` and carries its data layer (simulated or live). Because we generate the user data, the numbers show whether the pipeline recovers what we built in, not accuracy on real listeners.

## Risks

The biggest risk is that we cannot show real-data accuracy for the hybrid, so the plan is built to say that plainly instead of hiding it.

| Risk | Effect | Mitigation |
| --- | --- | --- |
| No real listening data exists for this catalog | No accuracy claim about real listeners is possible | Say so in the README; keep live events as a small real-data check; show results across the visible_share sweep |
| Simulated data is circular | Inflated CF numbers | Make the visible share of taste a parameter and sweep it; add noise and popularity bias; never claim real-world accuracy |
| Most live users are brand new | CF barely contributes in the demo | Onboarding by picking seed tracks; content-weighted blend by design |
| Text-only content features give weak similarity | Poor seed-track results | Add audio features; show the gain in the ablation |
| Dataset details differ from the plan (columns, licence, size) | Rework | Audit in Phase 0, pin the version and checksum |
| Dense similarity matrix memory | Crashes at larger catalogs | `NeighborIndex` interface; no full N × N matrix |
| Course deadline | Unfinished scope | Cut order: K-Means stretch, then live feedback, then the visible_share sweep, then FAISS |
| Dataset has no lyrics and genres only per artist | Weaker content similarity than a lyrics-based approach | Rely on audio features plus artist genre tags; show the ablation |
